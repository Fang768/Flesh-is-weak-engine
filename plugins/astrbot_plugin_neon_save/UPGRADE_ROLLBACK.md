# v0.2.1 升级、验收与回滚

## 升级前：保留正式 revision=6

1. 在旧版查询 `/neonstatus`，保存结果：revision=6、0名角色、not_started、team_cash=null。不要执行neoninit。
2. 完全退出AstrBot Desktop，确认后台也已停止。
3. 将整个 `~/.astrbot/data/plugin_data/astrbot_plugin_neon_save/` 复制到独立备份目录，包括SQLite、可能存在的-wal/-shm、exports；**只在停机后做文件复制**。实际位置若有自定义，以旧main.py调用的持久化路径为准。
4. 另行复制整个 `~/.astrbot/data/plugins/astrbot_plugin_neon_save/`，保留你当前已验证的v0.1.1代码，尤其main.py。不要用下载到的v0.1.0包替代你的回滚代码。
5. 保存这两份备份，标注时间与revision=6。不要把备份留在将要替换的插件代码目录中。

## 替换与验收

1. 解压v0.2.1 ZIP，将其中astrbot_plugin_neon_save下代码文件替换到原同名代码目录。不能多嵌套一层；main.py应在原插件目录最外层。
2. 不复制任何SQLite文件。ZIP没有数据库。不要卸载插件，避免宿主卸载过程清除数据。
3. 打开AstrBot；查看插件是否成功加载且显示0.2.0。
4. 正式群仅执行 `/neonstatus` 和 `/neontemplate 03`，应仍是revision=6、角色0名、第一幕未开启、现金未确认。若不符立即停止操作，保留日志与当前数据库，先回滚代码或排查路径，绝不新建覆盖。
5. `/neonbackup` 可生成整个数据库的一致备份。它不提升revision。
6. 在独立测试实例/独立测试群验收：认领→本人确认→管理员提交→入场→真实掷骰→伤害结算→重启查询→角色恢复；再验证普通玩家不能批准、缺少同意不能提交、过期/旧revision被拒绝、并发只能一份成功。
7. 正式群仅在你决定开始登记玩家后才执行neonclaim。该动作只是提案；同意后管理员批准才使revision从6变7。安装、查询和新增辅助表本身不升revision。

兼容依据：找到的原始ZIP含store.py（schema v1）；历史对话中的v0.1.1修复说明为仅修改main.py工具返回值。本地用该store.py建立revision=6空角色模拟库，验证升级不重写任何saves行、审计保留、旧版仍能读。**没有读取用户真实数据库，不能把模拟兼容验证等同于真实库逐字段审查。**

## 代码回滚（通常首选）

完全退出AstrBot，恢复升级前保存的v0.1.1代码目录，再启动。**保留当前plugin_data**。v0.2.1沿用schema v1，新增辅助表旧版会忽略；角色额外元数据为原equipment允许的JSON对象，不需要降级迁移。本地验证旧版存储可读，旧版完整UI尚未验收。回滚至旧版会恢复其旧命令权限模型，不应继续使用AI自动结算提示词。

如果升级后尚未批准任何提案，正式revision应仍是6；代码回滚不会改它。若已批准真实游戏变更，代码回滚不撤销游戏进度，revision保持最新值。

## 数据回滚（明确会丢弃备份之后的更改）

仅在确需整库恢复且已确认影响时使用：

1. 停止AstrBot；先复制当前整个plugin_data留档，防止丢失可恢复的新进度。
2. 将当前数据目录整体移到另一个目录，使用升级前完整、同一时间点的停机备份恢复目录。不要将旧主库和新-wal/-shm混用。
3. 同时恢复匹配的旧代码，再启动检查所有群。整库备份含其他群，不能只考虑一个群的进度。
4. 恢复revision=6的备份才会回到6。此为灾难恢复，会回退备份之后审计与进度；如果只需纠正角色，优先使用有新审计的restore_role提案，不做整库回退。

`database_backups/` 内SQLite在线备份是独立完整数据库，可在停机、归档当前目录后作为主库使用；不要附带旧进程残留的wal/shm。JSON exports只含快照，不是完整库备份，本版不开放直接覆盖导入指令。

## v0.2.0 → v0.2.1

同样先停机备份，替换代码；不执行SQL或数据迁移，不追补历史XP。启动仅检查状态，应保持原revision（若原来是6，仍为6）。旧任务提案的+2XP结果预览不再匹配，须重新提出并重新同意。回滚代码不会撤销已批准的新结算，也不会自动将3—6XP改回2XP。
