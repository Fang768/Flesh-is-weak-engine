# AstrBot 跑团插件 → NoneBot2 复用分析

对象：`D:\Code\Synthetic_Dawn` 下的 AstrBot 插件导出包（122 文件、约 10.2k 行 Python）。
目标：NoneBot2 + OneBot v11（NapCat）跑团机器人，并接入 DSH。

---

## 一、结论速览

| 模块 | 复用价值 | 处理方式 |
| --- | --- | --- |
| `dnd_dice` 骰池引擎（parser/roller/formatter/history） | ★★★★★ | **直接移植**，纯标准库，零 AstrBot 依赖 |
| `neon_save` 存档层（NeonStore / SafeStore / enrollment） | ★★★★★ | **直接移植**核心，替换数据目录与事件接入 |
| `nexus_gm/engine.py` 确定性检定 + 去重 + epoch | ★★★★★ | **直接移植**，是"程序定结果"的骨架 |
| `engine.py::PauseControl` 暂停/恢复授权 | ★★★★☆ | **直接移植** |
| `dynamic/` 动态第一幕（事件溯源 + 提案审核） | ★★★★☆ | **直接移植**，仅换调度入口 |
| `semantic.py` LLM 只提议不判定 | ★★★★☆ | 移植策略与校验，**替换 LLM 提供方为 DSH** |
| `conversation.py` / `voice.py` 人设与对话 | ★★★☆☆ | 移植提示词和拦截规则，替换调用层 |
| `public_guide/places/rule_reference` 公开资料 | ★★★☆☆ | 移植检索逻辑，语料改本地文件 |
| AstrBot 的 LLM 会话/知识库/人格管理 | ☆ | **不可复用**，NoneBot2 无对应机制 |

一句话：**游戏规则和存档这套"确定性内核"几乎可以整体搬走，需要重写的只有"平台接入层"和"模型调用层"两处薄壳。**

## 二、可直接移植（无 AstrBot 依赖）

### 1. 骰池引擎 `plugins/astrbot_plugin_dnd_dice`

- `dice_parser.py`：DiceGroup / RerollCondition 数据类，支持 `d20`、`4dF`、`kh/kl/dl/dh`、`adv/dis`、`!`/`!!`/`!p` 爆炸、成功计数、失败计数、`r/ro` 重骰、`s` 排序、多骰组与标签。
- `dice_roller.py`：`roll()` 完整投掷，产出 DieRoll / DiceGroupResult / RollResult，含爆炸、重骰、keep/drop、预算上限。
- `formatter.py` / `history.py`：结果排版与历史记录。
- `main.py`（820 行）：`/r`、`/roll`、`/dset`、`/rprefix`、`/rh` 命令与 LLM 函数工具 —— **只保留命令语义，注册方式要改成 NoneBot2 matcher**。

移植成本：几乎为零，只需把 `main.py` 的命令注册换成 `on_command`/`on_regex`，其余原样复制。

### 2. 存档层 `plugins/astrbot_plugin_neon_save`

- `store.py::NeonStore`：SQLite 事务、乐观锁 `revision`、`join/patch_many/dossier_task/reveal/history/export/restore`、`schema_version=1`、`rules_version=3.2`、快照白名单校验。
- `safe.py::SafeStore(EnrollmentMixin, NeonStore)`：可信骰点、`propose/proposal/consent/approve/approve_narrative`、`gate_state/pause_group/release_group`、资源结算 `apply`、`backup_database`。
- `enrollment.py`：认领/DIY 的"提案 → 本人确认 → 管理员批准"流水，含断线重放 `enrollment_replay`。
- `body_privacy.py`：私密字段的公开投影。
- `templates.json`：10 个预设角色（属性 BODY/REF/TECH/INT/COOL/EMP + 技能 + 义体上限）。

移植成本：低。要改的只有 `get_astrbot_plugin_data_path()` → `Path(__file__).parent / "data"`，以及对外抛事件的接口。

### 3. 确定性引擎 `plugins/astrbot_plugin_nexus_gm/engine.py`

- `class Engine(PauseControl)`：SQLite 表 `sessions/events/requests/archives/resume_requests/resume_consents`。
- 检定公式：`1d10 + 属性 + 技能 + 修正 vs DV14`；`SKILLS = {'工程':'TECH','调查':'INT','交涉':'COOL','潜行':'COOL'}`。
- 三幕场景 `SCENES`：接洽 / 取回 / 交付。
- 关键机制：消息 ID 去重、`action`/`natural` 两阶段（先公布 DV 再掷骰）、120 秒内文本指纹去重、epoch 失效校验、生成待审核草案 `player_flow/proposal`。

移植成本：低，纯逻辑。

### 4. 暂停/恢复授权 `engine.py::PauseControl`

- `checkpoint()`：对 `task,revision,roles,stage,round,done,pending,success,complete` 做 sha256。
- `request_resume` 生成 `rid + digest`（30 分钟有效）→ `consent_resume` 本人确认 → `approve_resume` 需管理员 + 全员确认 + gate epoch 校验。
- 数据库采用不可变式 epoch 递增。

移植成本：低。这是本项目最有价值的"防作弊"设计，建议原样保留。

### 5. 动态第一幕 `plugins/astrbot_plugin_nexus_gm/dynamic/`

- `engine.py::NarrativeEngine`：事件溯源（`sessions/journal/gate_reservations/advisories/requests`），剧情大纲来自 `dynamic/act1.json`。
- `adaptation(roles)`：按人数算并行目标数与敌方上限。
- 固有 gate 检查：`unlock/buy_key` 的 DV 由程序定，`buy_key` 扣 100€$ 走资源提案。
- `checkpoint()` 汇总成 operations 批量提案交人工审核；`auto_continue` 由 `narrative_auto.json` 白名单控制。
- `controller.py::DynamicController`：`interpret` 产出 mode/operation/node/question；`narrate` 限 220 字，DENY 正则拦截数字/预付/报酬/DV/骰点等；`decision.py` 强制字段与 mode 语义。

移植成本：低-中，逻辑自成体系，只需替换触发入口。

## 三、需要改造后复用

### 1. LLM 决策层 `semantic.py`

可复用：POLICY 提示词、严格 JSON 契约 `{mode,method,question,reason,sources}`、`parse_decision` 字段白名单、`sources` 必须命中真实 `chunk_id`、缺引用时一次 citation repair、NARRATE 只润色不得出现数字/成败/奖励、`call_metrics`/`semantic_audit`/`narration_audit` 审计表。

要改：`context.get_using_provider_async()` 换成 DSH 调用（见第四节）。**核心原则"LLM 只提议、程序定结果"必须保留。**

### 2. 对话与人设 `conversation.py` / `voice.py`

可复用：严格 JSON `{kind, reply}`、`parse_reply` 的越权拦截（自称玩家 / 编造申请状态 / 宣称已保存或给 DV）、`public_context` 组装、`STYLE` 语气规则、INTENT 闲聊与行动区分、NPC 声线 `mira/custodian`、`guard_decision` 口嗨转 clarify。

要改：模型调用层；`persona_manager` 无对应，提示词直接静态加载 `resources/TRPG_GM-system-prompt.txt`。

### 3. 公开资料检索 `public_guide.py` / `public_places.py` / `rule_reference.py`

可复用：检索与裁剪逻辑、chunk 组织方式。
要改：`kb_manager` 知识库换成**本地 markdown/JSON 语料 + 关键词或向量检索**（NoneBot2 无内置知识库）。

## 四、AstrBot → NoneBot2 接入层映射

| AstrBot | NoneBot2 等价物 |
| --- | --- |
| `astrbot.api.event.filter.command("x")` | `nonebot.on_command("x")` |
| `filter.platform_adapter_type == qq_official` | `GroupMessageEvent`（OneBot v11） |
| `event.message_str` / `event.get_group_id()` | `event.get_plaintext()` / `event.group_id` |
| `context.send_message(umo, MessageChain)` | `matcher.finish(...)` / `bot.send_group_msg(...)` |
| `context.get_using_provider_async()` | **DSH 调用**（自建 client 或 DSH 本地接口） |
| `persona_manager` | 静态系统提示词文件 |
| `kb_manager` | 本地语料 + 自建检索 |
| `get_astrbot_plugin_data_path()` | `Path(__file__).parent / "data"` |
| `AstrBotConfig` | `nonebot.get_plugin_config()` / pydantic 模型 |
| `star` 生命周期钩子 | `nonebot.get_driver().on_startup` |

## 五、"接入 DSH" 的两种候选路径

1. **DSH 作为 LLM 后端**：NoneBot 插件把 `semantic.py` / `conversation.py` 的 `model_call` 换成一个调用 DSH 的 HTTP 客户端（DSH 的 Web GUI 在 `http://127.0.0.1:4277`）。机器人仍是规则主体，DSH 只负责叙事与语义判定。
2. **DSH 作为会话主体**：QQ 消息转发给 DSH 会话，由 DSH 侧的 skill/工具驱动跑团。此时 `engine.py` 等确定性逻辑需要作为 DSH 工具暴露。

> 待确认：这条是本项目最关键的架构分叉，两条路的代码量差 3~5 倍。默认建议走路径 1（保留现有确定性内核，DSH 只做叙事），风险最低。

---

## 六、建议的重建顺序

1. 搬 `dnd_dice` 三件套 → 接 `/r` 命令 → 跑通骰点（半天，风险最低，立刻可验证）。
2. 搬 `NeonStore`/`SafeStore` → 建群存档、认领流程。
3. 搬 `engine.py` 检定与 epoch 去重 → 三幕流程跑通。
4. 接 DSH 做 `semantic`/`conversation` → 保留"只提议"约束。
5. 搬 `dynamic/` 第一幕 → 最后做，依赖前面全部。

## 七、风险与限制

- 原包 `Agent/docs/context/NOW.md` 明确：**无 AstrBot 4.29.4 宿主、无真实 QQ 群验收、完整战斗裁判未实现**。即原项目本身也未经真实群验证，移植时不能假设其行为已被生产验证。
- 第一幕含"固定可信机械操作"，移植后需重新核对 gate 数值。
- 骰点插件为第三方（保留原许可证），再分发需保留版权声明。
- AstrBot 的 `qq_official` 平台判定在 OneBot v11 下不存在，所有 `platform == qq_official` 分支要删掉或改为群事件判断。
